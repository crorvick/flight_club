# Deployment

Every commit merged to `master` is built into one Docker image, tagged with
its SHA, and pushed to GHCR.  That image is deployed to staging
automatically and promoted to production by hand.  Production never runs
anything that wasn't built and tested by CI and run on staging first.

```
pull request ────► checks (typecheck, lint, format, unit, E2E) + image build
merge to master ─► checks ─► build & push ghcr.io/…:<sha> ─► staging
promote.yml ─────► deploy the same <sha> ──────────────────► production
```

Each environment is a Render web service with its own Postgres database,
both defined in `render.yaml`, and its own bucket for squawk photos at an
S3-compatible storage provider (see [Photo storage](#photo-storage)).

The workflows live in `.github/workflows/`:

- `checks.yml`: shared by the other two so pull requests and `master` run
  the same checks, against a throwaway Postgres service container.
- `pr.yml`: checks, plus a Docker build (not pushed) to catch Dockerfile
  breakage before merge.
- `deploy.yml`: on push to `master`, checks, then build and push the image
  and deploy it to staging.
- `promote.yml`: run by hand with a commit SHA; deploys that commit's
  existing image to production.

Deploys go through `.github/actions/render-deploy`, which points the
environment's moving tag (`:staging` or `:production`) at the SHA image,
calls the Render deploy hook with that exact image, and waits until
`/api/health` reports the new SHA.  Render runs `node scripts/migrate.mts`
as the pre-deploy command, so migrations are applied before the new
version takes traffic, and a failed migration aborts the deploy with the
old version still running.  Likewise, if the new version fails its health
check, the old one keeps serving.

## One-time setup

1. **Publish the first image.**  Merge to `master` (or re-run the "Deploy
   to staging" workflow).  The image job pushes
   `ghcr.io/crorvick/flight_club:<sha>`; the staging job will fail because
   Render isn't set up yet.  That's expected.

   Create the `:staging` and `:production` tags once so Render has
   something to pull when the services are first created:

   ```sh
   image=ghcr.io/crorvick/flight_club
   docker buildx imagetools create --tag $image:staging $image:<sha>
   docker buildx imagetools create --tag $image:production $image:<sha>
   ```

   This needs `docker login ghcr.io` with a token that has
   `write:packages`.

2. **Give Render access to GHCR.**  Create a GitHub personal access token
   (classic) with only the `read:packages` scope.  In Render, under
   Workspace Settings → Container Registry Credentials, add it as a GitHub
   credential named `ghcr`.

3. **Create the Blueprint.**  In Render: New → Blueprint, select the
   repository.  This creates both web services and both databases, and
   generates each service's `BETTER_AUTH_SECRET`.

4. **Create the GitHub Environments.**  In the repository's Settings →
   Environments, create `staging` and `production`.  For each:

   - Secret `RENDER_DEPLOY_HOOK_URL`: the service's deploy hook, from
     its Settings page in Render.
   - Variable `APP_URL`: the service's public URL with no trailing
     slash, e.g. `https://flight-club-staging.onrender.com`.

   On `production`, add yourself (and any other officers trusted to
   release) as required reviewers, and restrict deployment branches to
   `master`.  Promotion then pauses for approval.

5. **Turn off Render's own auto-deploy** on both services if it's on.
   Deploys should only come from the workflows.

6. **Re-run the "Deploy to staging" workflow** and confirm it goes green.

7. **Make yourself an officer** on each environment, as described under
   [Approving members](#approving-members).

8. **Seed staging** with sample aircraft, flights and squawks, from the
   staging service's Shell tab in Render (never production's):

   ```sh
   node scripts/seed.mts
   ```

   It refuses to run if any aircraft already exist.

9. **Set up photo storage**, as described under
   [Photo storage](#photo-storage).  Until then everything works except
   attaching photos to squawks.

## Environment variables

The web service needs these at runtime.  `render.yaml` sets them when the
Blueprint is created; change them under the service's Environment page.

| Variable               | Value                                                      |
| ---------------------- | ---------------------------------------------------------- |
| `DATABASE_URL`         | The service's database, linked by the Blueprint            |
| `BETTER_AUTH_SECRET`   | Generated by Render, unique per service                    |
| `BETTER_AUTH_URL`      | Only for a custom domain; defaults to the onrender.com URL |
| `S3_ENDPOINT`          | The storage provider's S3 endpoint; omit for AWS           |
| `S3_REGION`            | Defaults to `auto` (R2); set the bucket's region for AWS   |
| `S3_BUCKET`            | The environment's photo bucket                             |
| `S3_ACCESS_KEY_ID`     | Access key with read and write on that bucket only         |
| `S3_SECRET_ACCESS_KEY` | Its secret                                                 |
| `GOOGLE_CLIENT_ID`     | Google sign-in; omit both Google values to leave it off     |
| `GOOGLE_CLIENT_SECRET` | Its secret                                                 |
| `APPLE_CLIENT_ID`      | Apple sign-in: the Services ID; omit both to leave it off  |
| `APPLE_CLIENT_SECRET`  | A JWT from `scripts/apple-client-secret.mts`, renewed twice a year |

Changing `BETTER_AUTH_SECRET` signs everyone out.  If any of the first
three is missing or invalid, the new version fails its health check and the
previous one keeps serving, so set them before deploying a commit that
needs them.

## Photo storage

Squawk photos are stored in an S3-compatible bucket rather than on the
service's disk, which Render wipes on every deploy unless a paid disk is
attached, and which would tie the service to one instance.  The bucket is
private: photos are only served through the app, to signed-in members.

Any S3-compatible provider works.  Cloudflare R2 is the suggested one: 10
GB of storage free, then a few cents per GB, and no charge for downloads.
For each environment:

1. **Create a bucket.**  In the Cloudflare dashboard, R2 Object Storage →
   Create bucket, named `flight-club-photos-staging` (or `-production`).
   Leave public access off.
2. **Create an API token for it.**  R2 Object Storage → Manage API tokens
   → Create API token, with the Object Read & Write permission applied to
   that bucket only.  Note the access key ID, the secret access key, and
   the S3 endpoint, `https://<account-id>.r2.cloudflarestorage.com`.
3. **Give them to the service.**  In Render, the service → Environment,
   set `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and
   `S3_SECRET_ACCESS_KEY`, then Save and deploy.

Report a squawk with a photo to check it works.

Locally and in CI the bucket is a RustFS container instead (see
`docker-compose.yml`), created by `pnpm storage:init`.

## Approving members

Anyone can create an account, but it starts inactive and without roles.
Officers approve new members, change role tags and deactivate members
on the Members page (linked from the home page, with a count of who's
waiting).  Every change is recorded in the audit log.

The first officer has to be made with the script in the image instead,
from the service's Shell tab in Render: sign up in the app, then run

```sh
node scripts/approve-member.mts member@example.com officer pilot
```

The roles given replace the member's current ones (`pilot`, `officer`);
with none, their roles are left as they are.  Locally, it's
`pnpm member:approve <email> [role...]`.

## Signing in with Google and Apple

Members can sign in with Google or Apple as well as a password.  Each is
offered only where its two environment variables are set, so either can
be left off.  Signing in with one the first time creates an account,
waiting for an officer's approval like any other.  A member who already
has an account links Google or Apple in Settings instead: the app never
verifies email addresses, so it won't join a Google or Apple sign-in to
an existing account on its own, and says so.

Each environment needs its own redirect URL registered with the
provider: the app's URL followed by `/api/auth/callback/google` or
`/api/auth/callback/apple`.

**Google.**  In the Google Cloud console, for a project of the club's:

1. **Set up the consent screen.**  Google Auth Platform → Branding: the
   app's name, a support email, and the app's domain.  Audience:
   External.  Data access: only the `email`, `profile` and `openid`
   scopes, which need no review by Google.  Publish it; while it's in
   testing, only the test users listed can sign in.
2. **Create a client.**  Clients → Create client, of type Web
   application, with the authorized redirect URI above for each
   environment it serves (`http://localhost:3000/…` too, for local
   development).  A separate client for production keeps a mistake on
   staging from touching it.
3. **Give it to the service.**  Set `GOOGLE_CLIENT_ID` and
   `GOOGLE_CLIENT_SECRET`, then Save and deploy.

**Apple.**  This needs the club in the Apple Developer Program (US$99 a
year).  In Certificates, Identifiers & Profiles:

1. **Register an App ID** with Sign in with Apple enabled.  It's never
   shipped; it's what the web sign-in hangs off.
2. **Register a Services ID**, such as `org.example.flightclub.signin`,
   with Sign in with Apple enabled and configured for that App ID: the
   app's domain (no `https://`) and the return URL above.  Apple only
   accepts HTTPS on a real domain, so there's no testing it on
   localhost; use staging.
3. **Create a key** with Sign in with Apple enabled, and download it.
   Apple lets you download it only once; keep the `.p8` file somewhere
   safe.  Note its key ID, and the team ID shown at the top right.
4. **Make the client secret** on your own computer:

   ```sh
   node scripts/apple-client-secret.mts <team-id> <key-id> <services-id> AuthKey_XXXX.p8
   ```

   It prints a JWT and the date it stops working, 180 days on: Apple
   allows no longer.  **Put a reminder in a calendar** to make a new one
   before then; when it lapses, Apple sign-in fails until it's replaced.
5. **Give them to the service.**  Set `APPLE_CLIENT_ID` to the Services
   ID and `APPLE_CLIENT_SECRET` to the JWT, then Save and deploy.

Apple lets members hide their email behind an address like
`x7k2q9@privaterelay.appleid.com`, which other members can't use, and
share their name only if they choose.  The app asks a new member with no
name for one, and Settings asks one with a relay address for their own
email.

## Resetting a password

Members change their own passwords in Settings.  One who can't sign in
has theirs set from the same Shell tab:

```sh
node scripts/reset-password.mts member@example.com
```

It asks for the new password twice without showing it, then signs the
member out of every session.  For a member who has only signed in with
Google or Apple, it gives them a password as well.  Locally, it's `pnpm member:password
<email>`.

## Promoting to production

If members will notice anything new, add an entry at the top of
`src/lib/release-notes.ts` first: a few short bullets in their terms.
Each member is shown every entry they haven't seen, once, in a "What's
new" popup the first time they open the app after the release.

Check the commit on staging first, on a real phone as well as a desktop.
Then:

```sh
gh workflow run promote.yml -f sha=<commit>
```

or run "Promote to production" from the Actions tab.  The SHA must be on
`master` and must already have an image (i.e. it was deployed to staging).

## Rolling back

Promote an earlier SHA.  The image still exists, so nothing is rebuilt.
Migrations aren't reversed, which is why they should be backward
compatible: add columns and tables in one release, and remove old ones only
in a later release once nothing reads them.

## Backups

### What's backed up

Render's paid Postgres plans take continuous backups with point-in-time
recovery: the database can be restored to its state at any moment in
the last few days (how many depends on the plan; see the database's
Recovery page).  Render keeps those backups itself, so nothing needs
scheduling.

For anything older, take your own logical backup now and then, e.g.
before a risky migration or at the end of each month:

```sh
# The database → Info → External Database URL (add your IP under
# Networking → Access Control first; the Blueprint allows none).
docker run --rm -v "$PWD:/backup" postgres:18-alpine \
  pg_dump --format=custom --file=/backup/flightclub-$(date +%F).dump \
  "<external-database-url>"
```

Keep the dump somewhere other than Render.  Remove your IP from the
access control list afterwards.

Photos aren't in the database backups.  R2 stores them redundantly, but
doesn't keep old versions, so a photo deleted from the bucket is gone.

### Restoring

A restore always makes a *new* database; the damaged one is left as it
is until you remove it.

1. **Restore into a new database.**  In Render: the database → Recovery
   → Point-in-Time Recovery → Restore Database.  Name it, e.g.
   `flight-club-production-db-restored`, choose the time to restore to
   (just before the mistake; at least ten minutes ago), keep the
   existing settings, and start the recovery.
2. **Check it.**  Once it's available, connect with psql (its Info page
   has the commands) and confirm the data you expect is there, e.g. the
   latest flights: `select date, billed_hours from flight order by
   created_at desc limit 5;`.
3. **Point the service at it.**  Copy the restored database's Internal
   Database URL into the service's `DATABASE_URL` (the service →
   Environment), and Save and deploy.  The deploy runs migrations, which
   does nothing if the restored database is already up to date.
4. **Keep the Blueprint in step.**  `render.yaml` still names the old
   database and links the service's `DATABASE_URL` to it, so a Blueprint
   sync could undo step 3.  Change the database's `name` in
   `render.yaml`, and the `fromDatabase` that refers to it, to the
   restored one's.  The restored database wasn't created by the
   Blueprint, so before applying the next sync, read the changes Render
   proposes on the Blueprint's page and make sure it isn't about to
   create or delete a database.
5. **Remove the old database** once everything is working against the
   restored one.  Until then it's a second copy you're paying for.

To restore one of your own dumps instead, create an empty database (or
use the restored one) and load it:

```sh
docker run --rm -v "$PWD:/backup" postgres:18-alpine \
  pg_restore --no-owner --clean --if-exists \
  --dbname="<external-database-url>" /backup/flightclub-2026-11-01.dump
```

Try the whole procedure once on staging, before there's real member
data to lose.
